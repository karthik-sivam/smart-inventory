### Current behavior that must remain intact

- Owners with no valid version-1 business profile receive a one-time required full-screen prompt after authentication.
- If language onboarding is required, it finishes before the business-profile prompt appears.
- The existing empty-inventory post-login onboarding waits until the business profile has been checked or completed.
- Invited members viewing another owner's workspace are not forced to describe that business.
- The required prompt cannot be interactively dismissed.
- Business type is required.
- Indian State / Union Territory is required.
- Business types currently include Supermarket / Grocery, Pharmacy / Medical Shop, Automobile / Auto Parts, Electronics / Electrical, Retail / General Store, Wholesale / Distribution, Restaurant / Cafe, Manufacturing, and Other.
- Selecting Other requires custom text, capped at 80 characters.
- Phone / WhatsApp is optional and is not OTP-verified.
- A supplied phone number must be in international format beginning with `+`, normalize to 7–15 digits, and cannot be saved without explicit contact consent.
- Clearing the phone field also clears the consent toggle.
- Owners can reopen the editable version through **Profile → Business details**.
- A completed version-1 profile does not reappear merely because the user signs out and signs back in; completion is stored in Firestore across devices.

### Persistence contract — do not break during a UI-only revamp

Business profile data is stored as a nested map on the authenticated person's document:

```text
users/{authenticatedUID}.businessProfile
```

Current keys:

```text
schemaVersion
businessType
otherBusinessType
state
phoneNumber
contactConsent
consentVersion
consentSource
consentUpdatedAt
completedAt
updatedAt
```

`FirestoreManager.personalUserRef()` is intentional: personal contact data must never be written to the owner of a team workspace the member happens to be viewing.

When no consented phone is present, `phoneNumber`, `consentVersion`, and `consentSource` are stored as null values and `contactConsent` is false.

### Amplitude privacy contract — do not send PII

Events:

- `business_profile_prompt_shown`
- `business_profile_completed`
- `business_profile_updated`
- `business_profile_save_failed`

Allowed Amplitude traits/properties include profile version, business type, State, whether a phone was provided, whether contact consent was given, source/audience, and completion duration.

Never send either of these to Amplitude:

- The phone / WhatsApp number
- Custom text entered for Other

### UI revamp freedom

The next session may change layout, typography, illustration/icon treatment, card styling, progress/step structure, picker presentation, field grouping, explanatory copy, keyboard behavior, validation presentation, loading state, and save-button treatment.

Keep these distinctions clear in the redesigned UI:

- Required: business type and State.
- Optional: phone / WhatsApp.
- Consent appears only when a phone number has been entered.
- Saving cannot proceed with an invalid phone or without consent when a phone is present.
- Required mode has no Cancel/skip affordance; edit mode does.
- A save failure keeps the form open and gives the user a retry path.

Prefer an iOS-native, compact SMB-friendly experience. Avoid turning this into a long questionnaire or adding number of locations—the CEO explicitly excluded that field.

### Presentation sequencing risks

`InventoryAppView` can coordinate three full-screen experiences: initial onboarding, language onboarding, and the business profile, followed by post-login onboarding. Do not introduce a second presentation owner or make multiple covers true simultaneously.

The business-profile check deliberately waits briefly after authentication, then reads Firestore. On a temporary fetch failure it does not lock the user out; it retries on a later authentication session or cold launch.

### How to test the one-time prompt

A completed profile is supposed to suppress the prompt. Signing out and in again is therefore not a reset mechanism after a successful save.

Use one of these approaches for UI testing:

1. Sign in with an account whose `users/{uid}.businessProfile` field does not exist.
2. In a non-production Firebase test project, remove only the `businessProfile` field for the test user.
3. Temporarily use a higher `BusinessProfile.currentSchemaVersion` on a throwaway branch, then revert it before committing.

Do not delete an entire production user document merely to retest this form.
